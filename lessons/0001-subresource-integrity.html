Subresource Integrity

Lock your CDN dependencies to their exact known content — so a compromised CDN can never run code on your page.

The attack in one sentence

Your index.html loads three scripts from external CDNs — globe.gl from unpkg, GSAP from cdnjs. Each of those CDNs is a third party you trust unconditionally: whatever they serve, your visitors' browsers execute.

A supply chain attack exploits that trust. The attacker doesn't hack your repo — they compromise the CDN (or the npm package it serves). The file at the same URL now contains malicious code. Every visitor to your portfolio runs it, because nothing on your page checks whether the file changed.

Real precedent
In 2024, the polyfill.io CDN was purchased by a Chinese company and began serving malware to 100,000+ websites within months. Sites with SRI hashes were automatically protected; sites without it ran the malicious code silently.

How SRI stops it

Subresource Integrity adds a cryptographic fingerprint to your <script> tag. The browser downloads the file, hashes it, and compares the result to your fingerprint. If they don't match — even one byte difference — the browser refuses to execute the script entirely. 

<script
  src="https://cdnjs.cloudflare.com/.../gsap.min.js"
  integrity="sha384-g4NTh/Iv5PPU4xPyhEWqPcwtNXOvdaDI8LLnyYfyNZOjKJeYQyjzQ9X5275eBjpt"
  crossorigin="anonymous"></script>

The integrity value is sha384- followed by a base64-encoded SHA-384 hash of the file's exact bytes. The crossorigin="anonymous" attribute is required — without it, the browser won't share the hash across origins.

Why SHA-384?
SHA-256, SHA-384, and SHA-512 are all supported. SHA-384 is the practical sweet spot: longer than SHA-256 (harder to collide), shorter than SHA-512 (smaller HTML). MDN recommends SHA-384 as the default.

Generating hashes

Two ways to get the hash for any file:

Option A — Terminal (one-liner)

curl -s https://example.com/lib.js \
  | openssl dgst -sha384 -binary \
  | openssl base64 -A

Pipe the output to sha384-<output> in your integrity attribute.

Option B — Online generator

srihash.org — paste the URL, get the full attribute string. Useful for quick checks.

Never trust a hash you didn't compute yourself
Some CDN providers display "suggested" SRI hashes on their pages. If the CDN is already compromised, that hash may match the malicious file. Always compute hashes from a fresh download, or verify against a second source (npm registry, GitHub release).

Your task — apply SRI to the portfolio

Here are the three ready-to-use <script> tags for your index.html. The hashes were computed from a fresh download today. Replace the existing unsecured tags with these: 

<!-- globe.gl 2.41.5 -->
<script
  src="https://unpkg.com/globe.gl@2.41.5/dist/globe.gl.min.js"
  integrity="sha384-r1nelv9C/mkJJ6yKy5ReigAikWpnLgtZTQkkda8oss6akerAHOC/KRtDkBtg4Z1V"
  crossorigin="anonymous"></script>

<!-- GSAP 3.12.5 -->
<script
  src="https://cdnjs.cloudflare.com/ajax/libs/gsap/3.12.5/gsap.min.js"
  integrity="sha384-g4NTh/Iv5PPU4xPyhEWqPcwtNXOvdaDI8LLnyYfyNZOjKJeYQyjzQ9X5275eBjpt"
  crossorigin="anonymous"></script>

<!-- GSAP ScrollTrigger 3.12.5 -->
<script
  src="https://cdnjs.cloudflare.com/ajax/libs/gsap/3.12.5/ScrollTrigger.min.js"
  integrity="sha384-Z3REaz79l2IaAZqJsSABtTbhjgOUYyV3p90XNnAPCSHg3EMTz1fouunq9WZRtj3d"
  crossorigin="anonymous"></script>
After updating — verify in browser
Open DevTools → Network tab → reload the page. Click each CDN script entry. If you see Status: 200 with no console errors about integrity, SRI is working. To confirm it blocks bad files, temporarily change one character in an integrity value — DevTools will show a red "Failed to load resource: integrity check failed" error. Then revert.
